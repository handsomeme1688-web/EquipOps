## 1. 项目背景与目标

### 1.1 背景

制造企业的设备资产分散在各生产部门，设备台账长期依赖 Excel 台账与纸质报修单维护，存在三类问题：

1. **台账失真**——设备的位置、责任人、状态变更没有系统留痕，盘点时对不上账。
2. **报修链路不可追踪**——报修靠电话或口头传达，从报修到修复完成之间没有状态记录，无法回答「这台设备停机多久了」「谁在处理」。
3. **维修知识不沉淀**——同类故障反复发生，每次都靠老师傅的经验，人员流动即知识流失。

### 1.2 目标

构建一套设备运维平台，覆盖**设备台账管理**与**维修工单全生命周期**两条主线，并提供基于企业维修资料的 **AI 辅助诊断**能力。

具体目标：

- **G1** 设备台账线上化，任一设备的基本信息、归属部门、责任人、当前状态可查、变更可追溯。
- **G2** 报修工单全流程线上流转，任一时刻可查询工单处于哪个环节、由谁负责、已耗时多久。
- **G3** 建立基于部门的数据隔离，员工只能看到与自己职责相关的数据。
- **G4** 提供 AI 维修助手，基于企业设备手册与历史维修案例回答故障处置问题，答案必须可溯源。
- **G5** 系统具备可观测性与可测试性，故障可定位，变更有回归保障。

### 1.3 数据来源与合规声明

本系统为**独立重构项目**。业务语义参考自公开的设备管理领域常识与脱敏后的需求描述，**不包含任何原企业的源代码、表结构、生产数据、账号凭据或内网地址**。

AI 服务使用的语料限于**明确允许使用的公开设备手册**与**自行编写的脱敏故障案例**，不使用任何企业内部资料。

### 2.2 本期不做（Out of Scope）

**明确列出不做的部分，与列出要做的部分同等重要。** 以下能力在原始业务域中存在，但本期不实现：

| 不做项 | 原因 |
|---|---|
| 设备点检与保养计划（日/周/月点检、点检异常、保养操作、点检补做） | 独立子域，工作量与工单相当，纳入会导致主线深度不足 |
| 量测设备与辅助治具管理（定期校验、校验申请与签核） | 同上，且与核心目标关联度低 |
| 多级签核流程引擎（可配置的审批流定义） | 通用工作流引擎是独立技术命题，本期用固定状态机替代 |
| 设备报废与资产转移流程 | 涉及财务资产口径，超出运维范畴 |
| 前端界面 | 本期交付后端 API 与接口文档，前端仅提供最小验证页面 |
| 多租户 SaaS 化（跨企业隔离） | 本期为单企业内部系统，仅做部门级隔离 |
| 移动端与小程序推送 | — |

## 3. 术语表

| 术语 | 定义 |
|---|---|
| 设备（Device） | 纳入管理的生产设备实体，具有唯一设备编号，归属某一部门，有指定责任人 |
| 设备编号（Device Code） | 设备的业务唯一标识，人工编制，全系统唯一，不可重复 |
| 工单（Repair Order） | 一次报修请求的完整生命周期记录，从报修发起到关闭 |
| 维修记录（Repair Record） | 工单处理过程中的一次具体操作留痕，一张工单可有多条 |
| 委外 | 本单位无法自行修复，转由外部厂商处理的处置方式 |
| 验收 | 报修方对维修结果的确认行为，通过则工单完成，不通过则退回重修 |
| 数据隔离 | 用户只能访问其所属部门范围内数据的机制 |
| 权限码 | 形如 `资源:动作` 的字符串，是授权判定的最小单位 |
| 幂等 | 同一请求重复提交多次，产生的业务效果与提交一次相同 |
| 知识库 | AI 助手检索的语料集合，由设备手册与历史故障案例构成 |

## 4. 角色与权限

### 4.1 角色定义

| 角色 | 说明 | 典型用户 |
|---|---|---|
| 普通员工 | 设备的日常使用者，发现故障后发起报修 | 一线操作工 |
| 部门主管 | 管理本部门设备与人员，审核本部门报修 | 车间主任 |
| 维修工程师 | 承接并执行维修作业 | 维修班组成员 |
| 维保主管 | 管理维修资源，审批委外申请，确认最终验收 | 设备科负责人 |
| 系统管理员 | 管理账户、角色、权限、部门，不参与业务流转 | IT 管理员 |

### 4.2 权限模型要求

- **R4.1** 采用 RBAC 模型：用户与角色多对多，角色与权限多对多。
  即便初期业务上每人只配一个角色，**模型必须支持多角色**，用户的有效权限为其所有角色权限的并集。
- **R4.2** 权限的最小单位是权限码，形如 `device:view`、`order:accept`。
- **R4.3** 权限判定必须在服务端完成。前端隐藏按钮不构成授权，任何接口都必须独立校验。
- **R4.4** 权限变更（角色改权限、用户改角色）后，受影响用户的权限在**下一次请求时**即生效，不得因缓存导致旧权限持续可用。

### 4.3 数据可见范围

| 角色 | 设备可见范围 | 工单可见范围 |
|---|---|---|
| 普通员工 | 本部门设备 | 自己发起的工单 |
| 部门主管 | 本部门设备 | 本部门发起的全部工单 |
| 维修工程师 | 全部设备（只读） | 待受理工单 + 自己承接的工单 |
| 维保主管 | 全部设备 | 全部工单 |
| 系统管理员 | 全部设备 | 全部工单 |

- **R4.5** 数据范围过滤由服务端强制施加，**不接受前端传入的部门标识作为过滤依据**。
- **R4.6** 直接按主键访问单条记录时，同样必须校验数据范围，越权访问返回 403 或 404，不得返回数据。

## 5. 业务流程

### 5.1 工单状态

| 状态 | 含义 | 是否终态 |
|---|---|---|
| 待受理 | 报修已提交，尚无人承接 | 否 |
| 已接单 | 维修工程师已承接，尚未开始作业 | 否 |
| 维修中 | 正在执行维修 | 否 |
| 委外中 | 已转外部厂商处理，等待返回 | 否 |
| 待验收 | 维修完成，等待报修方确认 | 否 |
| 已完成 | 验收通过 | **是** |
| 已关闭 | 无需维修或异常终止 | **是** |

### 5.2 主流程（Happy Path）

```
报修提交 → 待受理 → 已接单 → 维修中 → 待验收 → 已完成
```

### 5.3 分支与例外流程

| 分支 | 触发条件 | 结果 |
|---|---|---|
| 委外 | 维修中，工程师判定无法自修，提交委外申请并经维保主管批准 | 转入「委外中」，厂商处理完毕后回到「待验收」 |
| 验收不通过 | 待验收，报修方判定未修复 | 退回「维修中」，重新处理 |
| 撤销报修 | 待受理，报修人主动撤销 | 转入「已关闭」 |
| 误报关闭 | 待受理，主管判定无需维修 | 转入「已关闭」 |

### 5.4 状态流转业务规则

- **R5.1** 工单状态只能沿已定义的合法路径流转。任何跳跃式变更（如「待受理」直接到「已完成」）必须被拒绝。
- **R5.2** 终态工单不可再发生任何状态变更。
- **R5.3** 状态变更必须由专门的领域服务集中校验，业务接口不得直接写入状态字段。
- **R5.4** 每次状态变更必须留下记录：变更人、变更时间、变更前后状态、备注。
- **R5.5** 不同的状态变更动作要求不同的权限码，且要求操作者处于合法的数据范围内。

> **开发者任务**：以上定义了状态集合与业务规则，但**合法流转边的完整矩阵**（哪些状态可以到哪些状态）需要开发者据此推导并固化为代码与测试断言。非法边必须逐条有测试覆盖。

## 6. 功能需求

编号规则：`FR-<模块号>-<序号>`。每条需求应可被至少一条自动化测试验证。

### 6.1 M1 认证与授权

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-1-01 | 用户可使用账号密码登录，登录成功签发访问令牌 | 密码错误返回明确业务错误，不泄露账号是否存在 |
| FR-1-02 | 密码必须以不可逆的方式存储，且相同明文密码的存储值不同 | 不得使用 MD5/SHA 等无盐快速哈希 |
| FR-1-03 | 访问令牌具有较短有效期，配合可轮换的刷新令牌延长会话 | 刷新令牌使用一次后即失效 |
| FR-1-04 | 用户注销后，其已签发的令牌立即不可用 | 注销后携带旧令牌访问返回 401 |
| FR-1-05 | 用户修改密码后，此前签发的全部令牌立即失效 | — |
| FR-1-06 | 被禁用的账户不能通过令牌继续访问 | — |
| FR-1-07 | 未携带令牌、令牌过期、令牌签名被篡改，三种情况均返回 401 | 三种情况须分别有测试 |
| FR-1-08 | 已认证但无相应权限的请求返回 403 | 401 与 403 语义不得混用 |

### 6.2 M2 组织与账户

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-2-01 | 管理员可维护部门信息（增删改查） | 部门下存在用户或设备时不允许直接删除 |
| FR-2-02 | 管理员可维护账户，账户必须归属某一部门 | 账号名全系统唯一 |
| FR-2-03 | 管理员可维护角色 | 角色名唯一 |
| FR-2-04 | 管理员可为角色分配权限，支持批量调整 | 分配操作必须整体成功或整体回滚，不得出现部分生效 |
| FR-2-05 | 管理员可为用户分配角色，支持一个用户多个角色 | 用户有效权限为多角色权限并集 |
| FR-2-06 | 用户可查询自己的权限集合 | 用于前端渲染，但不构成授权依据 |

### 6.3 M3 设备台账

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-3-01 | 可创建设备，需指定设备编号、名称、型号、归属部门、责任人 | 设备编号重复时返回冲突错误（409） |
| FR-3-02 | 可修改设备信息 | 设备编号一经创建不可修改 |
| FR-3-03 | 可删除设备 | 设备存在未终态工单时不允许删除 |
| FR-3-04 | 可按主键查询设备详情 | 不存在返回 404；越权返回 403 或 404 |
| FR-3-05 | 可分页组合检索设备，条件包括名称模糊、编号精确、状态、部门、责任人 | 未填写的条件不参与过滤；返回结果受数据范围约束 |
| FR-3-06 | 检索结果需包含部门名称与责任人姓名等关联信息 | 不得由前端二次查询拼装 |
| FR-3-07 | 可为设备上传说明书、图片等附件 | 见 FR-3-08 至 FR-3-10 |

| FR-3-10 | 下载附件前必须校验对该设备的数据访问权限 | 跨部门下载必须被拒绝 |
| FR-3-11 | 对外输出的设备数据不得直接暴露数据库实体的全部字段 | 列表与详情均须经过输出对象转换 |

| 编号 | 需求 | 验收要点 |

### 6.7 M7 AI 维修助手

| 编号 | 需求 | 验收要点 |
|---|---|---|

## 7. 非功能需求

### 7.1 安全

- **R7.1 越权防护**：所有涉及数据访问的接口，均须同时校验「有无权限」与「在不在数据范围内」。仅校验其一视为缺陷。
- **R7.2 输入校验**：所有外部输入须白名单校验，非法输入返回字段级错误提示。数据库访问须使用参数化查询。
- **R7.3 幂等**：创建类写操作须支持幂等。**幂等的正确性不得仅依赖缓存组件**——缓存不可用时，重复请求仍须只产生一条业务记录。
- **R7.4 凭据管理**：任何密钥、密码、令牌不得硬编码于代码或配置文件，须由运行环境注入。
- **R7.5 AI 安全**：提示注入防护不得以关键词过滤为主要手段，须依靠工具白名单、参数结构校验、最小权限、二次确认与服务端授权。查询类工具须使用只读数据库账户。模型不得生成并直接执行数据库语句。

### 7.2 性能

- **R7.6** 性能指标须在固定环境下实测得出，测试条件（硬件、数据量、并发数、运行时参数、预热策略）须记录在案，每组重复不少于 3 次并保留原始数据。
- **R7.7** 高频只读数据可引入缓存，但须先证明访问频率与收益，不得无差别缓存。
- **R7.8** 缓存与数据源之间的不一致窗口须被识别并记录，须说明缓存操作失败时的补偿方式。
- **R7.9** 大数据量下的组合检索须有支撑索引，索引选择依据须有执行计划佐证。

### 7.3 可靠性

- **R7.10** 对外部依赖（AI 模型服务、缓存、消息中间件）的调用须设置超时，重试须有限次数且带退避，且仅对可重试错误重试。
- **R7.11** 任一外部依赖不可用时，系统须以可预期的方式降级，而非整体不可用。
- **R7.12** 应用启动不得强依赖非核心组件。

### 7.4 可观测性

- **R7.13** 提供健康检查端点，可区分「进程存活」与「可对外服务」。
- **R7.14** 采集核心业务指标：请求量、错误率、工单流转量、缓存命中率。
- **R7.15** 每个请求分配唯一追踪标识，该标识须出现在响应中并贯穿该请求产生的全部日志。

### 7.5 可测试性与可交付性

- **R7.16** 核心业务须有自动化测试覆盖，重点覆盖权限、事务、并发、幂等、状态流转、失败路径。
- **R7.17** 集成测试须使用真实的中间件实例，不得以内存替代品代替生产同类组件。
- **R7.18** 数据库结构变更须通过版本化迁移脚本管理，从空库执行迁移可完整重建当前结构。禁止运行时自动改表。
- **R7.19** 项目须可一键启动全部依赖，具备健康检查。
- **R7.20** 代码提交须自动执行编译与全部测试。
- **R7.21** 代码库不得包含任何真实凭据，须有检查手段保证。

## 8. 约束与假设

### 8.1 技术约束

| 项 | 约束 |
|---|---|
| 运行时 | Java 17 及以上 |
| 应用框架 | Spring Boot 4.x（3.x 已于 2026-06-30 全线结束开源支持） |
| 安全框架 | Spring Security 7.x |
| 数据库 | MySQL 8.x |
| 架构形态 | 模块化单体，按业务域分包，不拆分为独立部署的微服务 |
| AI 服务 | 独立进程，通过网络接口与主服务交互，不与主服务共享数据库连接 |

### 8.2 假设

- 单企业内部使用，用户规模在千人量级，设备规模在万台量级。
- 部门层级结构相对稳定，不存在频繁的组织架构重组。
- 网络环境为企业内网，不面向公网开放。
- AI 语料的更新频率较低，允许离线批量构建索引。

## 9. 验收标准

### 9.1 功能验收

- 第 6 章全部功能需求均已实现，且每条至少有一条自动化测试对应。
- 完整业务旅程可端到端跑通：登录 → 查询设备 → AI 咨询故障 → 查询维修历史 → 生成报修确认 → 确认报修 → 通知送达 → 审计可查。

### 9.2 质量验收

- 全量测试通过，且连续多次执行结果稳定。
- 从空数据库执行迁移可完整重建结构。
- 一键启动后可通过健康检查并完成冒烟验证。
- 代码库凭据扫描无命中。

### 9.3 安全验收

以下攻击场景须全部被拒绝，且每条已固化为自动化回归用例：

| 场景 | 预期 |
|---|---|
| 跨部门查询设备列表 | 查不到 |
| 按主键直接访问其他部门设备 | 403 / 404 |
| 使用过期令牌访问 | 401 |
| 使用签名被篡改的令牌访问 | 401 |
| 重复使用已消费的刷新令牌 | 失败 |
| 权限被回收后使用旧令牌访问 | 拒绝 |
| 重复提交同一报修请求 | 只产生一条记录 |
| 缓存组件不可用时重复提交 | 仍只产生一条记录 |
| 多人同时接同一工单 | 仅一人成功 |
| 工单跳跃式状态变更 | 拒绝 |
| 通过 AI 诱导查询其他部门数据 | 拒绝 |
| 重放 AI 写操作确认凭证 | 失败 |
| 上传伪装扩展名的可执行文件 | 拒绝 |
| 跨部门下载设备附件 | 拒绝 |

### 9.4 故障演练验收

以下依赖分别停止时，系统行为须符合预期并有记录：AI 服务、缓存、消息中间件。

## 10. 已知限制

本文档所定义的系统存在以下已知限制，须在项目文档中如实说明，不得回避：

1. 单实例部署，定时任务在多实例场景下会重复执行。
2. 仅支持部门级数据隔离，不支持跨企业的多租户隔离。
3. AI 知识库使用原型级向量存储，未做生产级容量与高可用设计。
4. 审批流程为固定状态机，不支持业务方自助配置。
5. 性能数据来自单机固定环境，不代表生产集群表现。
